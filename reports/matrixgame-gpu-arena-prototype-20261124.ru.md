# Оптимизация GPU: состояния и прототип upload-арены

Основание: аппаратный профиль r42 показал 3060 ожиданий в ограниченном
окне, каждое из-за лимита 64 draw-пакета. Этот лимит ограничивает число
одновременно живых SDK mappings; само повышение лимита без изменения
владения GPU-памятью может вернуть прежний отказ.

В рабочем backend добавлено повторное использование scissor и неизменного
multisample-состояния в пределах одной записи. При новой записи и gamma эти
данные сбрасываются; scissor также сбрасывается перед clear и bind targets.
Счётчики повторного использования выводятся с остальной диагностикой.
devkitA64 compile/link: PASS, ELF сохранён отдельно; NRO не выпускалась.
Модель 4096 переходов состояния: host ASan/UBSan и ARM64/QEMU PASS;
физический GPU не запускался.

Отдельно создан экспериментальный CPU-планировщик общего upload-блока.
Он пока НЕ подключён к рабочему backend и НЕ изменяет лимит draw, обращения
к deko3d или время ожидания. Проверены выравнивание настоящего формата
NativeDrawUpload, неперекрытие размещений и маркеры данных, отказ добавления
после отправки, сохранение данных после неуспешного ожидания, повторное
использование только после успешного завершения. Для синтетических 4096 draw
получено 19 эпох на блоках по 4 МиБ. Это число не является измерением FPS,
аппаратных mappings или результата настоящего боя. Host ASan/UBSan и
ARM64/QEMU PASS.

Чтобы уменьшить реальные ожидания, ещё необходимо безопасно подключить
владение общими блоками к NativeDrawUpload и queue/fence, сохранить ресурсы
при ошибке отправки или ожидания, учесть превышающие размер арены загрузки,
бюджет и число SDK объектов, затем провести интеграционные проверки.
Итоговая корректность и производительность на Switch: HARDWARE PENDING.
