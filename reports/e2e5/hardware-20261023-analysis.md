и новостями планеты. Это не нормальная прозрачная подложка этих экранов.

Префикс файлов — `scene-40986867502-`. Contact sheets и точный metadata timeline
сохранены в приватном `build/hardware-20261023/`. Таким образом, ошибочная картинка
**уже есть в CPU composition/upload input**, а не впервые возникает в SDL/GPU.
Это существенно сильнее прежнего прогона 21.10: тогда UI был видимо испорчен,
но bounded scene probe не дал сопоставимых снимков нужного перехода.

Ранжирование обновлено:

1. Сохранённое изображение внутри UI-дерева (`SavedBackgroundControl`, BGBuf,
   `CopyScreenRectToBuffer`/`BindExternalGraphBuf`) либо неверное владение им:
   чистый framebuffer получает чужой контент именно при Draw UI. Это **ведущая
   гипотеза**, а не установленная строка-виновник.
2. Содержимое/владение resource cache или привязка графического контрола:
   новый холст чистый, но один из рисуемых источников уже содержит генерацию.
3. Ошибка обхода/рисования UI или запись через неверно привязанный CPU buffer.
   Следующая host-проверка должна отличить это от неверного исходного cache image.

Гипотеза «только предыдущая экранная GPU-текстура» не объясняет зафиксированный
CPU-дефект. Общая очистка framebuffer также не лечит контент, добавляемый позже.
В имеющихся выборочных ui-cache events нет однозначного source_owner,
указывающего на Introduction; нет `load-from-screen-failed`, доказывающего такой
отказ. Точный ошибочный control/resource key и виновный исторический commit
**пока не найдены**. Прежняя регрессионная граница из E2E-5.16.1 этим прогоном не
сужена. Предположительная правка основного рендера не вносилась.

## Карта: зависание принято, точная причина не установлена

Пользователь уточнил: не двигался даже указатель; звук не проверялся. Это не
следует переименовывать в «просто медленную анимацию». Однако до конца записанной
карты screen=16 интервалы остаются p50/p95 18.724/21.642 мс, max272.234 мс
в первом запуске и 18.279/24.254, max281.759 мс во втором. Приказ/film и ходы
302→305→306 в первом журнале наблюдаются. Затем состояние 306/film203/order0
долго ожидает, но ожидание приказа само по себе не доказывает зависший worker.
В первом журнале есть ещё переходы map→GameMenu→Achievements; полного shutdown
там нет. Между последней доставленной записью и фактическим зависанием остаётся
непокрытый интервал; очереди теряли samples. Полный freeze не воспроизведён host.

Следующий адресный offline repro: **копия нового AutoSave** → те же несколько
ходов/приказов, с проверкой завершения ThreadCalc, входа/выхода turn-film,
InputContextScope и настоящего обновления world/UI. Сравнить конечные состояния
и блокировки, а не только смену календарного дня. Не менять таймер или потоки
на основании одной гипотезы. Текущий статус причины — UNRESOLVED.

## Сохранение и клавиатура

Во втором запуске строка 5963 (mono_us=42034291833):
`manual-publish: byte copy failed: No such file or directory`; rollback завершён,
new generation retained in temp. Аналогичный отказ есть и при предыдущей
попытке. Журнал подтверждает отсутствие commit, а сообщение об ошибке правдиво.
Транзакция уже прошла сериализацию, валидацию, создание journal/manifest/ready;
упала публикация `save.tmp → destination`. В первом запуске есть и успешная
manual-save transaction; её target в логе не указан, поэтому это не отдельное
доказательство успеха пользовательского ручного слота вместо autosave.

**Новая адресная проверка:** настоящий существующий `ValidateSave` под
ASan/UBSan/leak detection прочитал все четыре присланных файла:
AutoSave.sav, AutoSave.sav.bak, RecoveredSave-1.sav, save.tmp — **PASS** структуры
RSG/EZ, bounds, zlib и CRC32. Файлы не заменялись и не мигрировались. Проверка
не равна полному игровому load и не доказывает корректность всего состояния.

Старый CopyBytesExclusive объединяет fopen(input), open(destination), fdopen,
read/write/close в один диагноз. По имеющемуся ENOENT нельзя строго отличить
открытие source от создания destination; путь/байты имени и точная фаза не
записаны. Предварительно **вероятнее** destination/path, поскольку source
проверен непосредственно перед этим, но race тоже не исключён. Подмена имени
латиницей не является доказанным решением. Следующая правка должна сначала
сохранить исходный errno + точную failed phase/path bytes, затем проверить
именно этот путь на копиях новых файлов (Unicode и ASCII), сохранность temp,
старого слота и journal. Менять формат сейва/обнулять состояние оснований нет.

Причина отсутствия языкового переключения найдена отдельно:
`swkbdConfigMakePresetDefault` выбирает `SwkbdType_QWERTY` (это документировано
в установленном `swkbd.h:360`). После preset теперь явно задаётся SwkbdType_All.
Настройки языка консоли не изменяются. **Настоящий OSK backend ARM64 COMPILE PASS**,
не host-имитация раскладки. Переключение и ввод кириллицы остаются HARDWARE_PENDING.
Исправление OSK не объявляется исправлением ENOENT.

42040639950, Rendering/audio closed42040860532, Closing platform42040977590,
Game shutdown complete42041138891. Участок занимает около 549 мс.
Есть INVALID HANDLE lookup token=0 между закрытием rendering/audio; фатальность
этой строки не установлена. Затем runtime stats; heartbeat writer существует
как минимум до42050293882 (ещё9.155 с). **Возврат в hbmenu не подтверждён.**
Пользователь подтвердил отказ HOME и принудительное выключение Power. Нельзя
объявлять ни «успешный выход», ни виновную прошивку по этим данным. Область для
проверки: после ProgramMain, диагностика FirstFailure/BootReady, остановка/join

для сравнения потребуется записать её версии, не объяснять ею дефект заранее.

## MatrixGame GPU smoke: HARDWARE FAIL до draw

Полный log: BEGIN a224fa4 → `deko image alignment exceeds prototype allocator`
→ END status=FAIL code=1. Это исключение из конструктора DekoMeshRenderer при
создании color/depth layouts. Shader/device/queue prefix был пройден, но реальный
VO upload/indexed draw/readback этим прогоном **не подтверждены**. FAIL не является
отрицательным результатом самого draw: до него не дошли.

Найденная ошибка: сравнение image-layout alignment с DK_MEMBLOCK_ALIGNMENT=4096.
Это разные требования. В deko3d [dkImageInitialize](https://github.com/devkitPro/deko3d/blob/master/source/dk_image.cpp)
проверяется alignment **offset внутри memblock**; специальный depth memory kind
требует big-page alignment. Здесь каждое изображение имеет отдельный Image
memblock, offset=0, поэтому ограничение прототипа необоснованно. Управление GPU
mapping выполняет [сам deko3d](https://github.com/devkitPro/deko3d/blob/master/source/dk_memblock.cpp).

Убраны эти три ошибочные проверки в render target и texture paths; выделение
по layout.getSize(), Image flags, offset0 и RAII сохранены. Новый алгоритм боя,
fallback или фиктивный успешный draw не добавлены. **devkitA64 COMPILE/LINK PASS**
в существующем matrixgame-native-init-probe, strong undefined=0.
В ELF удержан настоящий constructor/texture upload; это не проверка исполнения
draw/readback и не отдельное доказательство retained indexed-draw path этого target.
Первый link без
DEVKITPRO не нашёл /opt/devkitpro/libnx/switch.ld; с DEVKITPRO=C:/devkitPro тот же
кандидат скомпонован. Физический повторный draw/readback — HARDWARE_PENDING.
Frozen smoke NRO/ELF/ZIP не заменены; нового NRO нет.

## Локальные изменения и следующие проверки

- `65c29fd` — MatrixGame dedicated image blocks: исправление alignment guard.
- `f43c90f` — Switch OSK All после QWERTY default preset.
- Без push/fetch. Основная игровая NRO/ELF, frozen GPU комплект, пользовательские
  saves/config/resources не изменены. Анализ и candidate objects — отдельно в build.

Приоритет: доказанный CPU background source → точная фаза save ENOENT →
post-shutdown/thread lifetime и map freeze. Для фона адресная host-регрессия:
generation с реальным текстом → planet/talk/shop/info, source controls/buffers
сверены до/после, первый неверный draw локализован; нормальная прозрачность
сохранена. Только после воспроизведения/доказанной причины — исправление.
Для сохранения: новый slot существует и CRC совпадает, реальный reopen/load на
копии, отказ не теряет прежние данные. Для выхода: bounded drain/join без живого
writer после return. Для GPU: SDK link уже пройден; следующий аппаратный критерий
— настоящий upload/draw/readback, recreate и `END status=PASS`.

Нового длительного тестирования на Switch сейчас не требуется. E2E-5.19 остаётся
активным offline направлением; исправление подготовительного GPU отказа не
считается запуском CGame::Init или планетарного боя.
