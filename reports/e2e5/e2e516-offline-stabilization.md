## P0: фоны и владение

Маршрут `29109eb4934e4c9483393969d4615ce5`: реальная новая игра,
генерация → персонаж → ангар → карта; два цикла корабль/меню/подтверждение
выхода/отмена/карта. **16 кадров** проверены по фактическим RGB565-хэшам.
В проверенных областях нет точных 64×64 фрагментов экрана генерации,
включая shaded/grayscale варианты; положительные контроли детектора
успешны. Две области замороженной подложки меню совпали после обоих
модальных возвратов: `[0,0]` изменённых пикселей в каждом цикле.
Это ограниченная проверка выбранных областей, а не всех возможных слоёв.

Проверены вход/выход самостоятельного и вложенного SceneCanvas,
`ScreenRenderBuffer`, стабильный per-scene/depth `AuxRenderBuffer`,
захваченный подготовленный снимок и заимствующий BGBuf. Полноэкранный
холст очищается при создании, не каждый кадр. На возврате вложенного окна
восстанавливаются указатели живого родителя и его подложка.

Причина исходного аппаратного дефекта не воспроизведена. Остались
следующие проверяемые гипотезы, по которым уже есть диагностические hooks:

| Гипотеза | Конкретный участок | Ожидаемое различающее свидетельство |
| --- | --- | --- |
| Старые пиксели остаются в основном холсте из-за неполного покрытия/инвалидации | `TMessageLoopGI::DrawQueuedUpdateRects`, `TfStarMap::DrawFrame`, `UpdateRects`, `ScreenRenderBuffer` | Чужой фрагмент есть в compose-before и переживает compose-after; present-input совпадает с ним |
| Чужая захваченная подложка возвращается через BGBuf | `CaptureScreenBackground`, `PreserveCapturedBackground`, `SceneCanvas`, `TGraphBufGI::BindExternalGraphBuf/Draw`, `AuxRenderBuffer` | Новый основной холст чист, но background-capture/restore или ui-cache-draw показывает чужой source_owner/неверную цепочку владельцев; фрагмент появляется при композиции |
| Скрытый отказ снимка оставляет неопределённое содержимое повторно выделенной памяти | `TGraphBufGR::LoadFromScreen`: catch → Clear → AllocateNative | `load-from-screen-failed` перед первым неверным BGBuf, непустая подложка после отказа. Сам отказ в этом прогоне не наблюдался |
| Ресурсный кэш/метаданные изображения повреждены при загрузке или вытеснении | `TCacheControlEC::AcquireDataFromConfig/DirectKey`, `TCGiEC`, `TGraphBufGI::Draw` | У корректного resource key неожиданно меняются размер/bpp/alpha/содержимое; при этом холст и capture ownership корректны |

**Графический fix на основании одной гипотезы не вносился.**

### Различия host/ARM64 по функциям

Под «последним проверенным host» здесь понимается ELF `4e826f10…fb81`,
который прошёл маршруты E2E-5.16, а не более ранний обычный host ELF
`8db92cee…bb54766`. Это существенно для GR_Main: старый host ещё не имел
всех performance hooks. Проверка использует сохранённый
`tested-host-composition.json` и manifest из самого итогового ZIP.

`GR_Main.cpp` у последнего проверенного host **не отличается** от ARM
effective source: SHA-256 обеих копий
`8ef52fc07043941a7895c2faa2ead87af901134ec9d39869cb08a64f73bf9580`.
Отдельно выполнен только preprocessing с фактическими сохранёнными
флагами GNU host и devkitA64. У 287 распознанных верхнеуровневых
определений функций GR_Main препроцессированные тела совпали; в том
числе отдельно извлечены десять функций графики/жизненного цикла/логов.
Это сравнение тел функций, не утверждение о совпадении ABI библиотек.

| Функции | Ветвь host | Ветвь Switch | Влияние и доказательство |

| `GetGameUserDirectory`, `GR_DXInit`, `FinalizeRuntimeAndSettings` | `SRHD_PORTABLE_RENDERER=1`, `__SWITCH__` отсутствует | `__SWITCH__=1`, `SRHD_PORTABLE_RENDERER` отсутствует | Общий guard `__SWITCH__ || SRHD_PORTABLE_RENDERER` истинен у обоих: portable user root, software renderer initialization, его shutdown. Графика/владение буферами затрагиваются, но выбранные тела одинаковы. Проверены preprocessing и реальные scene/map routes; GPU shutdown на host не проверяется |
| `CaptureScreenBackground` | Общий portable guard истинен | Общий portable guard истинен | Одинаковы `AuxRenderBuffer->LoadFromScreen`, shade/grayscale, затем `PreserveCapturedBackground`. Влияние на pixels и ownership, а не только диагностику. Подложки проверены двумя модальными возвратами и 16 кадрами выбранных областей |
| `EndFramePresentation`, `PresentScreenBuffer` | Общий portable путь с `PresentRgb565`, после него return | Тот же portable путь | Одинаковы глубина presentation, frame limit и указатель ScreenRenderBuffer. Старый D3D9 хвост остаётся в C++ после безусловного return и не исполняется. Карта проверена по 29 конкретным ROI; физический вывод этим не подтверждён |
| `AppendLogLineThreadSafe`, `AppendDebugLogLine`, `AppendLogTextThreadSafe` | performance overlay: AsyncLog и return | Тот же performance overlay | Только доставка диагностического текста. Отличие от старого обычного host состоит именно в этих трёх подменах, но в последнем проверенном host они уже присутствуют |
| `LogMemoryUsage` | Guard разрешает функцию; portable memory provider host | Guard разрешает функцию; memory provider Switch | Тело одинаково; отличаются данные платформенного поставщика статистики. Это диагностика, не содержимое framebuffer |

Не скрытая за совпадением GR_Main разница находится дальше по цепочке:
в `renderer_platform::PresentRgb565` **только Switch** компилирует
`SDL_CreateTexture(RGB565,STREAMING)` → `SDL_UpdateTexture(nullptr,pixels,pitch)`
всего буфера → `SDL_RenderClear` → `SDL_RenderCopy` → `SDL_RenderPresent`.
Host компилирует путь без этих вызовов; он подтверждает CPU-буфер и счётчик
presentation, а не экранную текстуру. Поэтому 29/29 совпавших ROI доказывают
правильный CPU input, но не успешный GPU upload/present.

Только host компилирует `E2E5_HOST_SDL_WINDOW`: mailbox, синхронные requested
PPM, `map516` и наблюдение текущего мира. Они читают пиксели/состояние,
а ввод передают через настоящий адаптер. Это тестовая инфраструктура с I/O
и затратами времени, а не часть Switch NRO. `E2E3_TRACE=1` у host и `=0`
у Switch также означает разную диагностическую нагрузку. Наличие
SDL/GPU на Switch — существенный непроверенный участок графики, а не
разница, которую можно отнести только к логированию.

`ab_StopLine.cpp` отличается содержательно только в
**`ab_StopLine::ab_StopLine_GetDistances`**, плюс include нового header.
Есть также механическая разница CRLF/LF; бинарные SHA выше её учитывают,
а функциональный diff нормализует только окончания строк.

- Host scene/map executable использует исходные два вызова
  `ProjectPointByMatrix(Matrix,&Line->First/Last->Position)` на каждой линии.
- ARM NRO добавляет lambda `project_endpoint`, локальный
  `StopProjectionMemo<TabStopPoint,TVector3D,...>` и заменяет эти два вызова
  на `endpoint_memo.Get`. Матрица, вычисление начала луча, фильтры глубины,
  пересечение линий, расстояния, обход/порядок и выходные параметры сохранены.
- `ab_StopLine_GetDistances` и header кэша не имеют развилки
  `__SWITCH__`/`SRHD_PORTABLE_RENDERER`. Candidate аркадного host тестирует тот
  же шаблон и те же два call sites, что ARM. Формат long double/реализация
  engine math между x86-64 и ARM64 остаются различными.
- Кэш по указателю действует только в одном query с неизменными точками
  и матрицей; 64 слота, без allocation, без кэша между тиками. Это настоящая
  оптимизация геометрии/столкновений аркады, **не диагностика**, не операция
  Screen/Aux framebuffer и не изменение количества тиков.
- Проверено обратное преобразование **всего translation unit** в исходный
  host текст, а не допуск имени файла в assert. Функциональный diff содержит
  ровно указанную lambda/локальный кэш/два call sites.
- Подтверждение: два 500-tick A/B с совпадением состояния/RNG/геометрии/
  кадров и 40960 сравнений настоящей engine projection в четырёх режимах
  округления. Сравнения flags ограничены sticky flags одного query; они
  не доказывают восстановление очищенных вызывающей стороной FP flags
  на отдельном cache hit. Полная игра на ARM64 не запускалась.

Среди 296 игровых единиц host только StopLine отличается от финальных
ARM sources; 295 остальных, включая GR_Main, совпадают побайтно.
`program.cpp` заменён host entrypoint, а в NRO присутствует настоящий
Switch entrypoint. В main NRO линкуются **297 исходных игровых объектов
+ 83 platform = 380**. EC_HsFile компилировался в full target, но исключён
из link response в пользу `ec_file_adapter`. Проверены реальные `.d`, а
не только список source-map. MatrixGame objects в этом response отсутствуют.

`build_dirty=true` не означает незафиксированный игровой fix: на момент
сборки `03651ce` tracked compiled-source tree был чист. Оставались только
пользовательские untracked `saves/` и `e2e510-artifact-provenance.json`;
ни один из этих путей не входит в dependency manifest или линковку.
Позднейшие `0996b17` и этот этап меняют отчёты/проверяющий инструмент;
они не превращают старую NRO в новый runtime. Manifest NRO по-прежнему
честно указывает source SHA `03651ced28ecf0125f0b62c4f8129bd71e27f5c8`.

### Насколько сужен интервал появления фонов

Последняя **вероятно** исправная по отсутствию жалобы аппаратная сборка —
`0fdf602` от 16 октября: её сохранённый hardware passport и E2E-5.8 отчёт
подтверждают завершение генерации, но последующий вход в игру не принят
отдельной проверкой фонов. Это слабая нижняя граница. Более сильный по
охвату станции/магазинов, но более старый ориентир — `9b691cb` от 16 октября.
Ни тот, ни другой нельзя назвать подтверждённо исправным по этому дефекту.

Максимально узкий **предполагаемый аппаратный интервал**:
`(0fdf602, 0c90081]`, 16→18 октября. Консервативный интервал с реально
посещёнными ранними экранами — `(9b691cb, 0c90081]`.
Сузить до `(0f91c1a,0c90081]` нельзя: один старый архив содержит оба запуска,
а привязки каждого скриншота/первого чужого фона к одному из них нет.

В узком интервале main-game кандидаты, а не все соседние MatrixGame commits:

- `1e47335`: загрузчики/файловые cleanup и переиспользование аркадной
  геометрии; изменение геометрии само по себе не объясняет фон станции.
- `f508742`: native-width payload/указатели, film/map и touch lifetime.
- `0f91c1a`, `3772031`: восстановление больших allocations, package/cache
  lifetime и учёт буферов. **Именно `3772031`** добавил одновременно exemption
  `EC_CacheBuf.cpp` в early-return guard генератора и
  `ResidentBytes=Buffer->Capacity`; у четырёх предыдущих перечисленных SHA
  этой effective правки нет. Это конкретный кандидат изменения поведения
  budget/eviction, но доказательства повреждения изображений не получено.
- Последний `0c90081` меняет script coercions/DWORD writes. Близость его даты
  к жалобе не устанавливает его причиной графического дефекта.

Сравнение renderer между `0fdf602` и `0c90081` не выявило изменения порядка
full SDL upload/copy/present; добавлялись host-only capture и метки/hash.
`ScreenRenderBuffer`/`AuxRenderBuffer` тогда были общими; отдельного
`SceneCanvas` ещё не было. Нынешние ownership fixes появились позже.
Отсутствие `SRHD_PORTABLE_RENDERER` в старых Switch flags действительно
существенно для кода под одним этим guard, например settings/reset path;
оно не является новым изменением внутри интервала и само по себе не
доказывает причину. Для текущих функций GR_Main проверено, что portable
ветвь включена и при одном `__SWITCH__`.

Ранжирование оставшихся гипотез — качественная оценка по имеющимся
скриншотам/исходникам, а не измеренные вероятности:

1. **Выше остальных: чужая сохранённая подложка/BGBuf ownership.**
   Узнаваемый цельный фон GameSettings повторяется за разными интерфейсами.
   Искать совпадение foreign pixels в background-capture/restore и первое
   ui-cache-draw с неправильным source_owner; одна очистка основного холста
   уже не решила аппаратный дефект.
2. **Высокая: старые pixels основного framebuffer/неполное покрытие.**
   Проверять compose-before → compose-after и update rects. Станция/меню
   могут продолжать рисовать UI поверх неверного базового слоя. На новых
   host-маршрутах самостоятельные холсты/возвраты отработали правильно.
3. **Средняя: resource cache lifetime/eviction при памяти Switch.**
   В частности новая accounting-ветка `3772031`, удержание BoundData и
   размеры/alpha/bpp. Нужен неверный cache content при правильных владельцах;
   совпадение размеров ресурса из старого отчёта не доказывает равенство bytes.
4. **Ниже: swallowed LoadFromScreen failure и повторно выделенные pixels.**
   Различающее событие `load-from-screen-failed` пока не получено.
5. **Ниже: SDL texture/upload/present на Switch.** Путь не менялся в
   исследованном интервале, UI продолжает обновляться. Но если CPU
   present-input чист, а фото экрана сохраняет чужой фон, эта гипотеза
   становится первой. Host и CPU snapshots GPU readback не заменяют.

Виновное изменение **не установлено**, фон не объявлен исправленным.
Нового крупного цикла renderer-разработки/пересборок не начинали.

### Краткое заключение и наиболее полезные будущие действия на Switch

- **Подтверждено офлайн:** байтовая копия сейва/сохранность при отказах;
  query-local оптимизация аркады с проверенной parity и −5.2…−8.0% Timer CPU
  на host; корректный CPU map route с движением и выбранные modal backgrounds;
  целостность уже выпущенного ARM64 пакета и конкретные отличия его кода.
- **Вероятно исправлено, нужна Switch:** ENOSYS failure сохранения;
  ожидается снижение CPU-затрат аркады. Новые hardware FPS и отсутствие
  ошибок сейва пока не подтверждены. Исправление повторяющихся фонов к этой
  категории не отнесено.
- **Без найденной причины:** аппаратный чужой фон и задержка карты при
  продолжающемся вводе; слой/условие отказа на новых diagnostics не получены.

Когда консоль появится, максимум информации дадут три коротких действия:

1. Новый запуск с `basic + scene on`: генерация → станция → карта → меню;
   фото первого неверного экрана и logs до перезапуска. Сопоставить фото
   с compose/background/present-input, определить CPU слой или SDL/GPU.
2. Отдельный запуск с копией готового сейва: станция → карта → один день
   и реальный приказ перемещения. Снять момент команды, дату и движение;
   сохранить logs/PPM, пока не исчерпаны первые 48 снимков этого запуска.
3. После перелёта сохранить копию с Unicode-именем, штатно перезапустить
   игру и загрузить её. Передать копии save/recovery-файлов и журнал —
   это отделит оставшийся ENOSYS-путь от иных причин отказа.

Это инструкция на будущее, не запрос аппаратного прогона сейчас.
Проверка: `tools/e2e5161_final_audit.py`, результат
`build/e2e5161/final-audit.json`, function diff/preprocessed inputs рядом.
Следующий самостоятельный этап — MatrixGame CPU-компоненты; основная
игра и её неизменяемый ZIP остаются зафиксированными отдельно.
