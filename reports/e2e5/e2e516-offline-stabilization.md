## Проверка реально собранного кода

Добавлен отдельный `--switch-effective` в `e2e5_host_game_build.py`.
Он использует ARM `effective-source-map.json`, фактический ARM
`link-objects.rsp` и ARM overlay/runtime headers. `program.cpp` заменён
host entrypoint; `EC_HsFile.cpp` исключён именно по ARM-линковке,
используется тот же portable `ec_file_adapter.cpp`.

Собраны 296 исходных игровых единиц, 35 platform и один host entrypoint:
**332 объекта**. В report сохраняются effective-пути, SHA-256 исходников
и объектов, флаги; dependency-файл каждого объекта проверяется на наличие
именно выбранного effective source. Исходный manifest сам по себе не
считался доказательством включения файла в executable.

Host отличается платформой x86-64/Linux, реализацией long double,
отсутствием Switch SDL/GPU presentation и host-only вводом/наблюдением;
`E2E3_TRACE=1` нужен маршрутам. Это не ARM64 runtime и не аппаратный PASS.
Тестировался host ELF `4e826f1076dadeba796ec89dee7750190b4caa110862ae5f04a7a77eed18fb81`.
Его игровой исходный состав взят из ARM preflight перед включением
оптимизации StopLine; графические effective-файлы соответствуют новому
кандидату. Оптимизация отдельно проверена настоящим движком аркады.

Драйвер адаптирован к `perf515-stage.log`. Синхронизация raw HID не ждёт
асинхронного журнала: host mailbox подтверждает реальное потребление ввода
отдельным `pad-ack.txt`. Во время удержания кнопки драйвер не читает большой
журнал. Это предотвращает искусственные повторы при автоматическом тесте;
управление Switch не изменено.

## P0: фоны и владение

Маршрут `29109eb4934e4c9483393969d4615ce5`: реальная новая игра,
генерация → персонаж → ангар → карта; два цикла корабль/меню/подтверждение
выхода/отмена/карта. **16 кадров** проверены по фактическим RGB565-хэшам.
В проверенных областях нет точных 64×64 фрагментов экрана генерации,
включая shaded/grayscale варианты; положительные контроли детектора
успешны. Две области замороженной подложки меню совпали после обоих
модальных возвратов: `[0,0]` изменённых пикселей в каждом цикле.
Это ограниченная проверка выбранных областей, а не всех возможных слоёв.

Проверены вход/выход самостоятельного и вложенного SceneCanvas,
`ScreenRenderBuffer`, стабильный per-scene/depth `AuxRenderBuffer`,
захваченный подготовленный снимок и заимствующий BGBuf. Полноэкранный
холст очищается при создании, не каждый кадр. На возврате вложенного окна
восстанавливаются указатели живого родителя и его подложка.

Причина исходного аппаратного дефекта не воспроизведена. Остались
следующие проверяемые гипотезы, по которым уже есть диагностические hooks:

| Гипотеза | Конкретный участок | Ожидаемое различающее свидетельство |
| --- | --- | --- |
| Старые пиксели остаются в основном холсте из-за неполного покрытия/инвалидации | `TMessageLoopGI::DrawQueuedUpdateRects`, `TfStarMap::DrawFrame`, `UpdateRects`, `ScreenRenderBuffer` | Чужой фрагмент есть в compose-before и переживает compose-after; present-input совпадает с ним |
| Чужая захваченная подложка возвращается через BGBuf | `CaptureScreenBackground`, `PreserveCapturedBackground`, `SceneCanvas`, `TGraphBufGI::BindExternalGraphBuf/Draw`, `AuxRenderBuffer` | Новый основной холст чист, но background-capture/restore или ui-cache-draw показывает чужой source_owner/неверную цепочку владельцев; фрагмент появляется при композиции |
| Скрытый отказ снимка оставляет неопределённое содержимое повторно выделенной памяти | `TGraphBufGR::LoadFromScreen`: catch → Clear → AllocateNative | `load-from-screen-failed` перед первым неверным BGBuf, непустая подложка после отказа. Сам отказ в этом прогоне не наблюдался |
| Ресурсный кэш/метаданные изображения повреждены при загрузке или вытеснении | `TCacheControlEC::AcquireDataFromConfig/DirectKey`, `TCGiEC`, `TGraphBufGI::Draw` | У корректного resource key неожиданно меняются размер/bpp/alpha/содержимое; при этом холст и capture ownership корректны |

**Графический fix на основании одной гипотезы не вносился.**

## P0: карта, состояние и конкретные области

Копия готового сейва имеет SHA-256
`bc6b1059a743800a4ae279356fd8d58968fd6948deaafc34dac02582b8a1f6b0`.
Оригинал и исходные CFG проверены неизменными после каждого маршрута.

Простой переход 360→361 (`ac4bb0f8084a45d3ae82f56e40362280`) подтверждает
смену дня, но игрок неподвижен. Этот результат не используется как
доказательство визуального движения мира.

Уточнённый маршрут `8c2313a5c4fa4a1f8c6162a40516f05a` выдал настоящий
приказ движения касанием свободной области карты, затем сделал ход:

- Игрок id=3: `(1139.374023438,3383.829833984)` → `(1349,3383)`.
- До рисования проверены пересечения области корабля с `UpdateRects`.
- Вокруг настоящего draw его control сравнивается содержимое clipped ROI.
- После `DrawQueuedControlRects` ROI отдельно сопоставляется с фактическим
  CPU-буфером, переданным Present; проверка требует один ship id **и тот же
  кадр** во всех фазах. Пустые/внеэкранные области исключены.
- **29 ship draw меняли пиксели; 29/29 видимых ROI совпали при выводе**.
  Для движущегося игрока подтверждены dirty → draw → composition → upload.
- Проанализировано 1490 записей; фильм прошёл до шага 203, вернулся в
  режим приказов. Модель других кораблей также менялась; внеэкранные
  объекты не считаются доказательством их видимого рисования.

Учтено, что расчёт устанавливает будущие позиции ещё при старом номере
дня: before/after сравниваются в завершённом `smmOrders`, отдельно от
переходных кадров `smmTurnFilm`. Пять тестов анализатора защищают от
ложного PASS по другой сущности, другому кадру, застывшему upload и
неверной границе модель/фильм.

Ни постоянной полной перерисовки, ни пропуска модели не добавлялось.
Host-путь проверен; аппаратная задержка карты остаётся HARDWARE PENDING.

## P1: аркада

Локальный commit оптимизации: `201c6ff04cc0959ba8feb60dc606ad613abb48f2`.
Дополнен короткий профиль: object physics, AI, DecideActions, collision
search, Ship::Advance/UpdateState, поиск врага, геометрия StopLine.
Профили inclusive и с выборкой; вложенные времена не суммируются.

Выбран `ab_StopLine_GetDistances`: соседние collision lines повторно
проецировали общие конечные точки одной неизменной матрицей. Теперь
фиксированный кэш на 64 записи живёт только в одном вызове. Совпадение
указателя возвращает точно тот же вектор, коллизия заменяет слот и
вызывает исходную функцию. Нет кэша между тиками, изменения формул,
порядка столкновений, RNG, удаления объектов или количества тиков.

| 500 одинаковых активных тиков | Timer CPU до, мс | После, мс | Изменение | Весь игровой поток до/после, мс |
| --- | ---: | ---: | ---: | ---: |
| Пара 1, baseline → candidate | 508.149 | 467.445 | −8.01% | 2496.802 / 2431.992 |
| Пара 2, candidate → baseline | 409.483 | 388.104 | −5.22% | 2112.552 / 2086.318 |

Две короткие пары; новых массовых серий нет. В обеих PARITY_PASS:
одинаковые selected object states и geometry checkpoints, 501 RNG-запись,
500 кадров и расписание случайных звуков. Полной сериализации каждого
внутреннего поля, реального ввода и аппаратной задержки эти контроли
не заменяют. В первой паре параллельно шла компиляция; вторая выполнена
без неё, обратным порядком, и сохраняет выигрыш Timer CPU.

С настоящей engine `ProjectPointByMatrix` выполнено 40960 bit/rounding/
sticky-flag сравнений в четырёх режимах округления, 25856 попаданий кэша;
sanitizer включён для теста/кэша, базовые объекты движка не пересобирались
под sanitizer. ARM64-компиляция проверяется отдельной Release-сборкой.
Это CPU-оптимизация host; новые FPS/темп симуляции на Switch не измерены.

повторную попытку и неизменность источника. Массовые fault-серии не повторялись.

и исходный untracked provenance не включались в коммиты.
